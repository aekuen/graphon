## 1. 问题背景

并行迭代节点在执行子图时，为每一项创建独立子引擎并提交到 `ThreadPoolExecutor`。当某个子图触发 `ChildGraphAbortedError` 时，父迭代节点会尝试中止其他兄弟子图并等待它们收尾。

排查发现两个独立缺陷：

1. **子引擎登记与取消之间存在竞争窗口**  
   Future 已进入运行态，但子引擎尚未写入 `started_child_engines` 时，兄弟任务触发 abort。取消方查不到引擎，只能调用 `future.cancel()`；而已运行 Future 的 `cancel()` 不会停止任务。随后引擎登记时也没有补查取消状态，导致 abort 永久漏发。

2. **dispatcher 的命令消费依赖事件**  
   dispatcher 启动时消费一次命令，之后只在成功、失败、异常事件到达时消费命令；空队列分支只休眠。若当前节点不产出终态事件，abort 留在命令通道中不被处理，`aborted` 标志不会置位，事件流不结束，父线程继续等待子 Future。

## 2. 改动点

### 2.1 `src/graphon/nodes/iteration/iteration_node.py`

| 位置 | 改动前 | 改动后 | 说明 |
|---|---|---|---|
| `_execute_parallel_iterations` | 只有 `started_child_engines` 与锁 | 新增局部 `aborted_reasons: dict[int, str] = {}` | 记录已发生的取消及原因 |
| `_submit_parallel_iteration_task` | 不传递取消状态 | 透传 `aborted_reasons` 和已有锁 | 工作线程登记后能补查取消状态 |
| `_handle_parallel_iteration_exception` | 不传递锁与取消状态 | 透传锁与 `aborted_reasons` 给兄弟 abort 处理 | 让取消路径与登记路径共享同一握手状态 |
| `_abort_parallel_siblings` | 直接读登记表；查不到就跳过 abort | 在锁内写 `aborted_reasons[index]`、查登记表并对已登记引擎发一次 abort | 消除“查不到引擎”导致的漏取消 |
| `_execute_tracked_iteration_parallel` | 登记引擎后立即执行 | 在登记锁内检查 `aborted_reasons`，命中则补发一次 abort | 覆盖“取消先于登记”的交错 |

关键细节：

- 复用已有 `started_child_engines_lock`，没有新增锁。
- `started_child_engines` 的参数类型保持 `Mapping`，未被无谓修改。
- `request_abort()` 只是向命令通道入队，不阻塞，因此放在锁内是安全的。
- 锁让“标记取消 + 查登记表”和“登记引擎 + 查取消标记”互斥，保证两条交错都只发一次 abort：
  - 取消先发生：登记线程补发；
  - 登记先发生：取消线程直接发。
- `_drain_parallel_siblings()` 未改动，仍保留等待语义。

### 2.2 `src/graphon/graph_engine/orchestration/dispatcher.py`

| 位置 | 改动前 | 改动后 | 说明 |
|---|---|---|---|
| `_COMMAND_TRIGGER_EVENTS` | 仅成功、失败、异常 | 增加 `NodeRunStreamChunkEvent` | 持续流式事件也能触发命令消费，对齐官方后续实现中的进度事件思路 |
| `_dispatcher_loop` | 事件队列为空时只 `time.sleep(0.1)` | 空队列时调用 `self._process_commands()` | abort 不依赖终态事件或队列为空之外的条件 |

命令消费时机现在与官方最新 `Dispatcher` 的结构一致：启动消费一次、触发事件后消费、空队列轮询消费、收尾再消费一次。

## 3. 为什么不做另一些改动

- **不给 `as_completed()` / `future.result()` 加 timeout**  
  timeout 不会停止任务，且 `ThreadPoolExecutor` 退出时仍会 `shutdown(wait=True)` 再等一次；吞掉超时会丢失 outputs 与 usage，抛出超时则把挂起变成失败且后台任务继续运行。

- **不改成 `try/finally + shutdown(wait=False)`**  
  `wait=False` 只跳过 join，不取消运行中的任务；线程池线程是 non-daemon，解释器退出时仍会 join。它把可见挂起变成后台泄漏和延迟退出。

- **不加 watchdog、强制杀线程、自定义 executor**  
  Python 无法安全强制终止线程；这些改动会引入新的生命周期与状态契约，超出本缺陷范围。

- **不改 `worker_pool.stop()`**  
  `stop()` 是全局停机信号，而这里需要针对某个子引擎命令通道发送 abort；改它会影响所有图执行，且无法解决登记竞争。

- **不改 `pyproject.toml`、`uv.lock`、`ai-dify` 配置、版本号、`rev`**  
  本次是 graphon 源码修复。`ai-dify` 通过 `uv.lock` 锁定提交，推送到 `master` 后单独更新锁定提交即可；默认分支已是 `master`，无需 `rev`，版本发布与依赖更新是独立流程。

### 7.3 优先级与依赖关系

建议顺序：**问题 4 → 问题 3 → 问题 2 → 问题 5**，问题 1 关闭。

原因：

1. 问题 4 是“根因型缺口”：外层 stop 根本没有下传路径；不先打通，问题 3 的检查点即使加在子图里也收不到通知。

4. 问题 5 是编辑器/日志配置问题，建议独立处理，不混入 abort 语义修复。

### 7.4 分问题方案

#### 7.4.1 问题 4：外层 abort 传播到已登记子图

**目标语义**：外层收到 `AbortCommand` 后，除了标记外层 `GraphExecution`，还要对所有由该执行创建且仍存活的子引擎补发一次 abort。pause 不在本轮范围。

**推荐方案**：通用子引擎注册表 + `AbortCommandHandler` 注入 fan-out 回调。

- 注册表放在 `GraphRuntimeState` 或 `GraphEngine` 均可，但**必须覆盖 `GraphRuntimeState.create_child_engine()`**，因为并行迭代直接走该入口（`iteration_node.py:501`、`graph_runtime_state.py:501-519`），只改 `GraphEngine.create_child_engine()` 会漏掉 iteration 子图。
- 使用 `weakref.WeakSet` + `Lock` 保存子引擎；子引擎完成后注销，避免悬挂引用。
- `AbortCommandHandler` 通过构造参数接收可选 `on_abort(reason)` 回调，不改 `CommandHandler.handle(command, execution)` 协议，避免波及 `PauseCommandHandler`、`UpdateVariablesCommandHandler` 和外部实现。
- 回调在锁外对注册表快照调用 `child.request_abort(reason)`；`request_abort()` 当前只是向自己的 `InMemoryChannel` 入队（`graph_engine.py:224-228`），非阻塞。
- fan-out 必须幂等：Redis stop 与层内 abort 可能同时到达；重复 `request_abort()` 不应产生重复终止事件。
- 注册表不得进入 runtime snapshot 序列化。

**不采用**：

- 让 child 共用外层 `RedisChannel`：违反单 engine 独占 channel 契约，且 Redis 侧没有 child task 路由。
- 只在 `IterationNode` 内轮询外层 `aborted`：只覆盖 iteration，不覆盖 loop/workflow-call，且无事件时可能观察不到。
- 在 `WorkerPool.stop()` 里 fan-out：正常结束也会调用，且没有 abort reason。
- 改 `ExecutionCoordinator.handle_abort_if_needed()`：当前无调用者，接入会改变生命周期契约。

**验证**：离线测试用 `InMemoryChannel` + `MagicMock` child builder，不发真实 Redis；覆盖“外层 stop → 两个 child 都收到 abort”“重复 stop 幂等”“child 完成后注销不再收到”。

#### 7.4.2 问题 3：把 abort 变成可观察的检查点语义

**目标语义**：不承诺抢占线程，只承诺**在下一个检查点停止继续调度新节点/新步骤**，并把生效时延写成“到最近检查点”。

**推荐方案**：

- 在 `Worker.run()` 取节点前检查执行是否已 aborted（`worker.py:101-112`）；已 aborted 则停止取新节点。
- 在 `Worker._execute_node()` 消费 `node.run()` 生成器事件时检查 aborted（`worker.py:129-178`）；abort 后停止继续拉取该节点后续事件并让 dispatcher 尽快进入终态。
- 对长耗时节点提供可选协作接口（例如 `supports_abort` 或 `check_abort()`），只在高风险节点接入：代码执行、工具调用、迭代/循环子图等待；普通纯计算节点不强制改。
- 保留 `abort()` 只改状态的实现，不引入 `ctypes` 抛异常、线程强杀等不安全手段。

**验收口径**：回归测试仍验证“同步代码不会被强杀”，新增测试验证“abort 后不会调度下一个节点、生成器在检查点停止消费”。不写“立即中断运行中同步代码”的承诺。

#### 7.4.3 问题 2：保留 usage，归并为问题 3 的检查点语义

**用户决策**：不接受 usage 丢失；问题 2 并入问题 3 一起解决。

**最终方案**：

- 不改 `_drain_parallel_siblings()`：已取消的 future 仍跳过，未取消的 future 继续调用 `result()` 收集 usage。
- 子图 abort 后的快速返回由 7.4.2 的 worker 检查点保证。
- 不加 timeout，不跳过 `result()`，不丢 usage。
- 边界：若同步节点没有检查点且无限阻塞，仍会挂；这是 Python 线程语义，不能在不丢 usage 的前提下规避。

#### 7.4.4 问题 5：logging 锁与调试器挂起

**结论**：不改 graphon 源码。graphon 只在 `debug_logging.py:157-161` 等处调用标准 logging，锁由 `logging.Handler` 提供。

**推荐做法（ai-dify 侧）**：

- 根 logger 配置 `QueueHandler` + `QueueListener`，业务线程只做短时入队，格式化与 I/O 在 listener 线程。
- 调试器配置跳过 `logging` / site-packages 内部帧，避免暂停在持锁的 `emit()` 内。
- 保留现有回归测试作为行为记录，不把它改成“graphon 修复”的断言。

**用户决策**：问题 5 本轮不修，不扩大范围；只保留上述建议。
